# data freshness audit: what updates when you change your book

Nov 12, 2026. Read-only audit of `main` at `796690fa` plus the uncommitted working tree as of this evening; files with uncommitted edits (the batch route, the alerts tab, the edit modal) may drift by a few lines. Every claim has a file:line. Nothing was written to any store.

## how the book is stored

Your "book" is five fields on `users/{uid}`:

| field | what | writers |
|---|---|---|
| `tracked_stocks` | every stock you follow (holdings and watching) | `app/api/watchlist/batch/route.ts:190-202`, `lib/radar-mutations.ts:96-104` (add), `:169-176` (remove), `lib/import/save.ts:169` |
| `watchlist_positions` | `{id: "holding" \| "watchlist"}` | same |
| `watchlist_holdings` | `{id: {quantity, market_value, average_cost, currency, source, updated_at}}` | same, plus `app/api/watchlist/holding/route.ts:71-79` (no caller in the app) |
| `watchlist_version` | counter, +1 on every book write | same |
| `covered_stocks` (+ coverage fields) | which stocks get levels and the full read on Free | the same transactions via `coverageAfterTrackChange`, and `app/api/coverage/route.ts` |

Next to the book, on the same doc: `theses` (reasons), `tax_lots`, `briefing_visits`, `followedSources`. Alerts and agents live elsewhere (see below).

There is also a per-user materialized copy, `tm_watchlist_views/{uid}`, with one row per stock (price, call, zones, brief tile, suggestions). It is rebuilt by `POST /api/watchlist/refresh` (`lib/watchlist-view.ts:2770-2864`) and by the backend job `backend/scripts/build_watchlist_views.py` (reads the same fields except `watchlist_holdings`, see bug 2, `:256-287`).

## the one thing to know first

Nothing in the app invalidates a cache on a book write. `revalidateTag`/`revalidatePath` appear only in `app/api/stock-request/route.ts:54-55` and `app/api/revalidate/route.ts:47-50`, never in a user write path.

That mostly works anyway, because:

- the LocalDB adapter keeps no data cache. It only shares a read that is in flight at the same moment (`lib/local-firestore.ts:170-174`) and bypasses Next's fetch cache on purpose (`:126-130`);
- every signed-in page that shows the book is `force-dynamic` and reads `users/{uid}` on each request through `getUserDoc`, which is React `cache()` (one request only, `lib/watchlist.ts:69-73`);
- signed-in requests never get the anon CDN copies: middleware only rewrites when there is no `tikrr_session` cookie (`middleware.ts:125-133`, `lib/anon-view.ts:1-12`);
- the three per-user memory caches (briefing, inbox, the old portfolio home) key on a fingerprint of the book (`lib/per-user-cache.ts:10-13`), so a book edit gives a new key.

So the live-read pages are fresh on the next server render. The problems are in four places: (1) the materialized `tm_watchlist_views` doc, which several surfaces read for rows and which is only rebuilt by some writers; (2) the Next client router cache and client-side stores that never refetch; (3) backend jobs and emails that read precomputed per-user docs; (4) write paths that change one thing and leave related data behind.

Every write also sets `tm_watchlist_view_refresh_control/{uid}` (`app/api/watchlist/batch/route.ts:258-269`, `app/api/watchlist/holding/route.ts:83-91`, `lib/radar-mutations.ts:32-44`, `app/api/import/save/route.ts:61`) and answers `refresh_queued: true`. Nothing in `app/`, `lib/`, `components/` or `backend/` reads that collection (grep: only writers and `lib/delete-user-account.ts`). It is a queue with no consumer.

## caching layers, one by one

**LocalDB adapter.** No cache. Reads in flight at the same moment share one request (`lib/local-firestore.ts:170-174`). It uses undici's own fetch so Next never puts store reads in its Data Cache (`:126-130`). Worst case: immediate.

**React `cache()`.** `getUserDoc` (`lib/watchlist.ts:69`), `getViewer` (`lib/entitlements-server.ts:37`), `getSessionUser` (`lib/auth-server.ts:143`). One request only. Worst case: immediate.

**`unstable_cache` / `sharedCache`.** Used only for shared market data and the example book: series 3 h, earnings 30 min, dividends 30 min to 6 h, goal returns 12 h, analysis mix 3 h keyed by weights, example portfolio 10 min, example inbox 10 min, OG card specs 5 min (`lib/portfolio-data.ts:55,90,270`, `lib/dividend-plan-data.ts:42,49`, `lib/goal/data.ts:40`, `lib/portfolio-analysis/load.ts:110,160,263`, `lib/inbox/server.ts:198`, `app/api/og/[...card]/route.tsx:115`). `lib/shared-cache.ts:5-12` forbids per-person data there, and I found none. Nothing per-user is tagged, so nothing needs a `revalidateTag` today.

**Per-instance memory.** `perUserCache` (`lib/per-user-cache.ts`) for the briefing (60 s, `lib/briefing-data.ts:539`) and the inbox (60 s, `lib/inbox/server.ts:131`); `lib/portfolio-home/server.ts:157` too, but nothing imports `loadPortfolioHome` any more. Keys fingerprint the book, so a book edit is immediate. Alerts, agent runs, reason checks and call changes are not in the keys and can lag up to 60 s. Per Vercel instance, so two instances can show different minutes. `lib/agent-jobs-data.ts:423` keeps shared collections (13F, insiders) 5 min; not per-user.

**force-dynamic vs static.** Every book page is `force-dynamic` (`app/(app)/portfolio/*/page.tsx`, `app/(app)/briefing/page.tsx:54`). The stock page sets `revalidate = 60` but reads cookies, so a signed-in render is dynamic.

**Anon CDN copies.** `/`, `/briefing`, `/explore`, `/portfolio` (no query) for cookieless GETs only (`lib/anon-view.ts:44-50`, `middleware.ts:124-133`). Checked on the dev server: `GET /portfolio` without a cookie answered `x-middleware-rewrite: /anon/1/portfolio`, `x-nextjs-cache: HIT`. Signed-in users never see these.

**Client router cache (Next 13.5.11).** A page you visited is reused for 30 s after its last use on soft navigation, and an AUTO prefetch shell for 5 min (`node_modules/next/dist/client/components/router-reducer/get-prefetch-cache-entry-status.js:23-50`). Browser back/forward always restores the old render. Only `router.refresh()` clears it. Nav links prefetch AUTO on hover (`components/oa/intent-link.tsx:19`); no `prefetch={true}` anywhere, so no 5-minute full prefetches. Which writers refresh:

## what each change does today

**Add a stock** (`POST /api/track` → `addRadarStock`, `lib/radar-mutations.ts:46-127`; or `/api/watchlist/batch`; or `/api/import/save`). One transaction writes `tracked_stocks`, `watchlist_positions`, `watchlist_holdings`, `watchlist_version`, coverage, `watchlist_events/{mutationId}` and `tm_tracked_instruments/{id}.tracked_count` (`radar-mutations.ts:62-118`). Then on-demand research is queued for covered stocks (`:122-124`) and the unread refresh-control doc is written (`:125`). My stocks, every `/portfolio/*` tool, the stock page and the inbox see it at once. The briefing, Ask's portfolio tool, MCP and the emails wait for the view: seconds when the browser triggers a rebuild, otherwise until the next weekday build.

**Remove a stock** (`DELETE /api/track` → `removeRadarStock`, `radar-mutations.ts:129-193`; or a batch without it). Removes it from `tracked_stocks`, positions, holdings and coverage. Leaves `theses`, `tm_thesis_checks`, `tax_lots`, `tm_alerts` and `tm_agent_jobs` scoped by ticker untouched. Live pages drop it at once. The Taxes page keeps listing it; alerts keep firing; ticker agents keep running; the inbox keeps agent and alert items 14 days; Ask/MCP portfolio keep it until the view rebuild.

**Edit shares or avg cost** (only through the batch modal now; `PATCH /api/watchlist/holding` has no caller in the app). The batch writes the whole `watchlist_holdings` map from what the modal sends and stamps `updated_at = now` on **every** holding (`app/api/watchlist/batch/route.ts:148-162`). Live pages are immediate. Ideas then treats every holding without tax lots as bought today (`lib/portfolio-ideas/server.ts:255-259`). Avg cost is not used by the briefing or the memo.

**Move Holdings ↔ Watching** (batch modal, or `/api/track` with the other `position_type`). Moving to Watching deletes the holding's numbers (`radar-mutations.ts:86`; the batch only keeps holdings for holding items, `batch/route.ts:148-162`). Live pages are immediate. Emails keep saying "you hold it" until the view rebuild. The reason stays and is still checked as "why you own it" (`lib/thesis.ts:137-141`). Ticker-scoped alerts and agents don't care.

**Price alert** (`POST/DELETE /api/alerts` → `lib/stock-alerts.ts:42-127`, docs in `tm_alerts`). Never checks the book. Alerts tab updates its own state; the inbox shows fired ones within 60 s. Evaluated every 15 min by `backend/mail/jobs.py alerts` (`install-mail-timers.sh:57`) or the old `backend/price_alerts.py`; neither reads `tracked_stocks`.

**Reason** (`POST/DELETE /api/thesis`, `app/api/thesis/route.ts:40-88`, field `users/{uid}.theses`). Must be on a tracked stock (`:53-55`). Every server reader filters to tracked stocks (`:32-33`). Checks are written on read (`app/api/thesis/checks/route.ts`) and nightly at 17:30 ET. The client store merges the saved reason at once (`components/thesis/store.ts:114-118`).

## bugs, ranked by user impact

1. **"Add to watchlist" on a stock you already hold demotes it and deletes your shares and cost.** `addRadarStock` sets the position to whatever was asked even when the stock is already tracked, and deletes the holding for "watchlist" (`lib/radar-mutations.ts:79-86`). Callers that always send "watchlist": theme/basket/compare/screener buttons (`components/screener/basket-actions.tsx:41`), landing picks (`lib/pending-picks.ts:106`), Ask's add action (`app/api/ask/action/route.ts:31`, which then replies "Already on your watchlist") and MCP add with no `position_type` (`lib/agent-intelligence.ts:849`). Silent data loss, no undo.
2. **Scheduled view builds wipe holding amounts from `tm_watchlist_views`.** `list_subscribed_users` selects fields without `watchlist_holdings` (`backend/storage.py:2175-2193`), so the job passes `holdings={}` (`backend/scripts/build_watchlist_views.py:276`). Twice every weekday the view loses every share count; a browser rebuild puts them back. Ask's `get_my_portfolio` and MCP `get_my_radar` read shares from the view (`lib/agent-intelligence.ts:638-644`), and radar weights become 0 (`backend/scripts/materialize_radar_views.py:398`).
3. **Alerts outlive their stock and can become invisible.** Removing a stock leaves its `tm_alerts` active; both evaluators ignore the book. (Partly by design: the stock page offers alerts on any stock, followed or not, `components/stock-report/report.tsx:593-604`.) Remove everything and My stocks shows the example, whose Alerts tab says alerts live with your own portfolio (`components/portfolio/alerts-tab.tsx:94-102`), so you can't even turn them off, but they still email.
4. **The earnings reminder toggle does nothing.** The stock page saves `kind: "earnings_24h"` and promises an email the day before (`components/stock-report/alert-controls.tsx:229-238`). No job reads that kind from `tm_alerts` (`backend/mail/alerts.py:550-561` is price only). The old sender did mail day-before earnings notes, but from `tm_lifecycle_events` that the view build queues for every tracked stock of a Pro user, toggle or not (`build_watchlist_views.py:70-106,117-119`, read at `backend/radar_alerts.py:46`), and it stops under `MAIL_V2_ACTIVE=1` (`backend/scripts/send_radar_alerts.py:14-17`). Mail v2 only sends earnings findings from agent runs. So under v2 nobody who turned the toggle on gets the email.
5. **Many add paths never rebuild the view**, so new stocks are missing from `/briefing` (or the whole page sits on "pending") and have no call in emails or Ask until the next weekday build, up to ~65 h over a weekend: onboarding, landing picks, theme/basket buttons, import, Ask, MCP. The refresh-control doc they write has no reader, and the API tells the client `refresh_queued: true` (`app/api/track/route.ts:128,177`).
6. **Emails ignore `watchlist_positions`** and use the view row's `position_type` (`backend/mail/data.py:243`): a holding moved to Watching is still written up as "you hold it" with the holding thresholds until the next build. And a user who removed every US stock gets the stale view rows back (`data.py:215-216`).
7. **Any batch save resets every holding's buy date** (`app/api/watchlist/batch/route.ts:159`), so Ideas shows every holding without lots as short-term and as a recent buy for wash sales (`lib/portfolio-ideas/server.ts:255-259`).
8. **The Python view writer has no version guard.** It overwrites with `merge=False` from a user snapshot read at the start of the run (`backend/storage.py:1959-1963`, `build_watchlist_views.py:243`), while the web writer refuses older versions (`lib/watchlist-view.ts:2843-2850`). A long run can write back a book from before your edit.
9. **Ask/MCP portfolio answers come from the view only** (`lib/agent-intelligence.ts:565-648`), with removed stocks, old Holding/Watching and (see 2) empty shares, while MCP `what_you_own` reads live. The two tools can contradict each other in one conversation.
10. **Ticker-scoped agents keep running on removed stocks** (`lib/agent-jobs-data.ts:340`), and their findings keep going to the inbox (14 days) and the alert email.
11. **Stale ownership on the stock page in the same tab.** The reasons store loads once (`components/thesis/store.ts:79-91`) and never reloads after a book change. After a removal it can still show your reason card; after a new holding, no "why do you own it" prompt until a full reload.
12. **Taxes keeps removed and watched stocks** with open lots and harvest suggestions (`lib/portfolio-tax-data.ts:56,73`); lots and holding shares can disagree, lots win (`lib/portfolio-tax.ts:417`).
13. **Users who untrack everything keep their last view forever** (the job skips empty `tracked_stocks`, `build_watchlist_views.py:258-261`), which feeds the mail fallback in 6.
14. **Theme/basket "Add to watchlist" doesn't refresh**, so My stocks and other pages you visited in the last 30 s show the old list on soft navigation.
15. **The bell can stay stale for a whole session**: no polling, reloads only after 5 min when the tab is re-shown or the popover reopened (`components/inbox/inbox-bell.tsx:29,133,226`).
16. **Alerts tab state isn't reset by `router.refresh()`** (`alerts-tab.tsx:79`), so an alert created from the stock page in another tab, or by Ask, doesn't show until a full reload.
17. Smaller ones:
    - Free user at the alert limit is told "You already have that alert" (`lib/create-alert.ts:47-49`).
    - Alerts never resolve when alert emails are off (`backend/mail/send.py:197`, `jobs.py:130`).
    - Account deletion leaves `tm_alerts`, `tm_agent_jobs`, `tm_agent_runs`, `tm_thesis_checks` (`lib/delete-user-account.ts:77-107`), and those agents keep running.
    - A re-added stock brings back its old reason and lots.
    - Dead code: `PATCH /api/watchlist/holding` has no caller; `lib/portfolio-home/server.ts` is unused; `/api/chat` has no caller and still falls back to the never-written `radar_v1` (`app/api/chat/route.ts:288`).
    - Docs say the view is built "pre-market + on-demand" (`backend/PIPELINE.md:37`); it is ~10:00 and after close on weekdays.

## fix plan

In order. Each is the smallest change that makes related surfaces agree after an edit. "VPS" means a backend change that needs `git pull` on `/opt/tikrr` and a service or timer restart.

1. **Never demote a holding by "adding".** In `addRadarStock`, when the stock is already tracked and the request is "watchlist", keep the current position and numbers (`lib/radar-mutations.ts:79-86`). Only the batch modal and an explicit move change Holding ↔ Watching. Add a test: add "watchlist" on a held stock keeps `watchlist_holdings[id]`. MCP turns a missing `position_type` into "watchlist" (`lib/agent-intelligence.ts:849`), so pass "not given" through as `undefined` if MCP should still be able to move a stock on purpose. Web only.
2. **Rebuild the view on the server after every book write.** In `addRadarStock`, `removeRadarStock`, the batch route and import save, call `rebuildAndSaveWatchlistView` through `afterResponse` (`lib/after-response.ts`) with the new `watchlist_version`; the web writer already drops a build older than the stored version (`lib/watchlist-view.ts:2843-2850`). The mutations don't return the new tracked list and positions today, so return them (or re-read the user doc inside the build; holdings are already re-read there, `lib/watchlist-view.ts:2714-2715`). Coalesce per uid: if a build is already running in this instance, run once more after it with a fresh read, rather than starting one per write; the version guard only drops older builds, it doesn't stop duplicates, and it can't see other Vercel instances. Mind the cost: each build can make an LLM call (`rewriteSuggestionWhys`, `lib/watchlist-view.ts:1504`) and writes a history doc before the guard runs, a basket add is one write per stock, and the modal and Follow button already call `/api/watchlist/refresh`, so those paths would build twice. That covers onboarding, landing picks, theme buttons, import, Ask and MCP in one place. Keep `/api/watchlist/refresh` for the client's second refresh. Web only.
3. **Fix the Python view build.** Add `watchlist_holdings` to the `select` (`backend/storage.py:2175`); before writing each user, compare the stored `source_version` and skip when it is newer than the user's `watchlist_version` read for this run (mirror `lib/watchlist-view.ts:2843-2850`). Do the check and the write in one transaction (the LocalDB adapter supports them), and compare against the user's current `watchlist_version` re-read there too, not only the stored view: most edits today never rebuild the view, so the stored `source_version` is often as old as the snapshot. Skip the directive-change and earnings events for a skipped user. Optionally also consume `tm_watchlist_view_refresh_control` in a 5-minute timer instead of deleting it. VPS.
4. **Make emails read the live book.** In `load_person` use `watchlist_positions` for holding vs watching (`backend/mail/data.py:243`), and drop the fallback to view rows when `tracked_stocks` is empty (`:215-216`). Skip view rows whose `source_version` is below the user's `watchlist_version` for calls (send the stock without a call rather than an old position). That part is too blunt: `source_version` is per view doc, not per row, so it drops every call after any edit until a rebuild, and the call in a row comes from the stock's shared intel, not your position (`backend/watchlist_view.py:813-817`), so it is still right once the position comes from the live book. Live positions alone fix the "you hold it" bug. VPS.
5. **Tie alerts to the book.** Evaluators skip alerts whose stock is not in `tracked_stocks` (`backend/mail/alerts.py:550-561`); the Alerts tab renders the user's alerts even when the book is empty (`components/portfolio/holdings-stream.tsx:101-107`). Don't delete alerts on removal; a re-add brings them back. Careful: alerts can be set on stocks the person never followed (bug 3), so a plain "not in `tracked_stocks`" skip silently kills those. Mark a stock's alerts paused when it is removed (unpause on re-add) and skip only those. Then either build the `earnings_24h` sender (read `tm_alerts` kind `earnings_24h`, send on the day before the stock's current earnings date, since `metadata.event_date` goes stale when a company moves its date) or hide the toggle until it exists. VPS for the evaluator and sender, web for the tab.
6. **Stop restamping buy dates.** In the batch route, keep the old `updated_at` when quantity and cost are unchanged (`app/api/watchlist/batch/route.ts:148-162`). Web only.
7. **One "book changed" signal in the browser.** A tiny helper every book writer calls after a successful save: `router.refresh()`, plus a window event that the reasons store listens to (reset `started` and reload, `components/thesis/store.ts:79`), the bell listens to (reload summary), and the Alerts tab keys on (`key` = alert ids, so `router.refresh()` resets it). Add it to the theme/basket button and the Ask action UI, which don't refresh today. `RADAR_TRACK_CHANGED_EVENT` (`lib/radar-track-events.ts`) already exists and is fired on adds by the modal, Follow button and onboarding; widen it to every write rather than adding a second event. Web only.
8. **Ask/MCP portfolio through the live overlay.** Make `getMyAgentRadar` build rows with `loadRadarRowsForUser` (`lib/radar-rows.ts:15`), which already filters to the book and overlays live positions, holdings and prices. Web only.
9. **Smaller consistency fixes.** Taxes and inbox: hide lots, agent runs and alert items for stocks no longer tracked (keep the data). Agents: show "not in your stocks" on a ticker agent whose tickers you removed, instead of silently changing scope (owner call). Account deletion: archive the user's agent jobs and deactivate alerts. Alert 409: tell the limit apart from a duplicate. Web only, except the deletion cleanup of backend-owned docs.
10. **Cleanup.** Delete or wire up `PATCH /api/watchlist/holding`, `lib/portfolio-home/server.ts`, `/api/chat`'s `radar_v1` fallback; stop returning `refresh_queued: true` until something reads the queue (or step 3 makes it true); fix `backend/PIPELINE.md:37`.

Not needed: `revalidateTag` on writes. No per-user data sits in Next's data cache, so there is nothing to tag. A separate "book version" counter is also not needed: `watchlist_version` already exists and the per-user caches fingerprint their inputs. It would help to bump it from `/api/coverage` too (it doesn't today, `app/api/coverage/route.ts:98-108`), so the view build and any future cache see coverage changes as a new book.
